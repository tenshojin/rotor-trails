# 多设备性能与运行逻辑检查（2026-11-20）

## 范围与结论

当前项目是静态网页游戏：TypeScript / Vite、three.js WebGPU（回退 WebGL2）、Rapier WASM。没有独立业务服务器、数据库或在线 AI。本次检查的是客户端底层运行逻辑、画质策略、帧循环、资源加载与释放，以及静态构建和发布配置；没有改动飞行物理、碰撞、导航、任务规则，没有发布上线。

## 已修复的问题

| 问题 | 修改与影响 |
| --- | --- |
| RTX 3050/3060、RX 6500 等仅凭代际名称就可能进入极高画质与光追 | 首次启动改为保守分档，不自动开启光追。笔记本、未知架构名、基础 Apple M 芯片从中档开始；触屏和已识别核显从低档开始。高档仅保留给可明确识别的较强型号，仍属启发式判断。 |
| 老玩家保存了旧的自动极高/光追设置，进图就承担过大负载 | 自动模式在加载地图前重新限制初始档位；不会提高已经自动降低的画质，也不覆盖手动模式。 |
| 只限制 DPR，4K/8K 或超宽屏在低档仍绘制大量像素 | 增加低/中/高/极高的总像素预算：921,600 / 2,073,600 / 3,686,400 / 8,294,400。维持 CSS 尺寸和视角比例，另遵守 WebGPU/WebGL2 的纹理、渲染缓冲与视口尺寸上限。 |
| 自动降档到低画质后无进一步措施 | 连续低帧率时降低低档渲染分辨率，最低 50%；严重低帧率加快下降。后台、回放和重新预热不参与判断。极慢设备不会因为每帧都超过半秒而永远被排除。 |
| 低画质调整分辨率仍重建后期管线 | 低档后期配置不再把渲染比例作为图结构变化；只调整画布尺寸，不因缩放重编译整套着色器。 |
| 手动画质与自动优化的控制不明确 | 设置页新增自动性能优化开关；手动改画质、光追或渲染分辨率后关闭，玩家可以重新开启。补齐中/英/日文，并修正低档“时间超分”和光追“几乎无开销”的说明。 |
| 隐藏页面仍可能接收 RAF 回调 | 隐藏时不绘图、不轮询输入、不更新音频；恢复时清空帧率累计和旧时间戳。 |
| 暂停菜单与主菜单在高刷新率屏幕上过度绘制 | 普通菜单与暂停状态最多 30 次/秒；飞行、拍照、回放、预热仍按原来的刷新节奏。物理固定步长未修改。 |
| 高清航拍下载或解码挂起，占住全部下载名额 | 每个切片 15 秒超时，取消时立即释放名额，迟到结果释放；高清索引 10 秒超时后回退基础影像。销毁后的调度器不能重新开始下载。 |
| 航拍加载失败时泄漏已经成功的贴图 | 并发批次等待所有结果后统一清理失败批次；每一步取得的地图纹理立即登记到卸载清单，后续辅助图失败也能回收。 |

## 可核查的变化

4K（3840×2160，DPR 1）、低画质、渲染比例 100%：

- 原公式：3840×0.8 × 2160×0.8 = 3072×1728 = 5,308,416 个渲染像素。
- 现公式：1280×720 = 921,600 个渲染像素，减少约 82.64%。
- 内置浏览器实际读取到的画布为 1280×720，CSS 尺寸仍为 3840×2160。
- 这是渲染像素数量变化，不是测得的 FPS 提升。物理、CPU 开销、贴图显存和驱动仍影响实际表现。

## 验证

- 最终全量测试：93 个测试文件、712 项测试全部通过；TypeScript 类型检查与生产构建通过。
- 单元与集成测试覆盖：设备像素预算、GPU 初始分档、低档动态分辨率、不重复构建后期、手动设置优先、后台时间重置、暂停菜单限帧、纹理失败回收、切片超时与迟到结果。
- 屏幕预算测试包括：390×844、844×390、1024×1366、1920×1080、3840×2160、7680×4320、16000×600，以及 DPR 1/2/3。
- 内置 Chromium 的 WebGL2 路径：训练场加载完成、开始飞行、暂停、设置页、分辨率调整与自动优化开关均可操作；日志检查未见警告或错误。
- 实际窗口尺寸检查：844×390 的低档画布为 675×312；390×844 为 312×675，页面宽度 390、未出现横向溢出；4K 窗口画布为 1280×720。
- 原有独立截图脚本未能建立调试连接，因此浏览器验证改用内置浏览器；未把失败的截图运行记为通过。
- 构建产物保留在本地 dist；未推送或部署。

## 尚需实机确认的范围

1. 尚未取得真实低配 Android / iPhone / iPad、Safari、Firefox 和不同核显的持续飞行帧时间、峰值内存与温控降频数据。窗口尺寸模拟不等于真实设备验证，也不能证明 WebGPU 与所有驱动组合都通过。
2. 大峡谷基础资源仍约 89 MB，基础航拍 core.webp 与 mid.webp 合计约 41.6 MB（压缩文件大小）。本次解决失败回收和高清切片挂起，没有将基础航拍重制为分辨率分档资源；首次下载与解码峰值仍应重点实测。
3. 极高画质的 4096 级联阴影、体积云和远景植被仍属昂贵选项。手动选择这些效果的玩家保留控制权，不保证弱设备能流畅运行。
4. 不存在可通过修改数据库查询、API 缓存来解决上述客户端掉帧的业务后端。本次未修改托管服务缓存规则或发布配置。

复现命令：`npm test -- --maxWorkers=2`、`npm run build`。

## 复核（2026-11-20）

- 修正：WebGPU 后端只报架构名（如 “nvidia blackwell”、“amd rdna-3”），原改动下这类独显一律从“中”起步。现在 Ampere 及以后的 NVIDIA、RDNA 3 及以后的 AMD 从“高”起步（仍不自动开光追、不自动给极高）；入门卡撑不住由飞行中的自动降档兜底。Turing、RDNA 2、Apple（WebGPU 只报 “apple metal-3”）仍从“中”起步。
- 修正：旧存档迁移标记 `requalify` 改动后没人读了，接回去：v3 之前停在“中”的旧存档仍按显卡重新选一次。
- 格式：设置页新增几行的缩进和周围对齐。
- 实测（无头 Chrome，WebGPU）：主菜单和暂停菜单约 30 帧，飞行中不限帧；手动改画质后“自动性能优化”自动关掉，重新勾上能生效；0 个控制台错误。界面交互回归 36/36。
